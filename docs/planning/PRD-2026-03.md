# **1\. Executive Summary**

The Blender X3D import/export addon — currently maintained as a community extension targeting X3D 3.3 (2015) and VRML 2.0 (1997) — is the sole bridge between the world's most widely-used open-source 3D DCC tool and the ISO/IEC X3D ecosystem. Its present state is functionally inadequate for modern use: texture export is non-functional, physically based rendering is unsupported, animation export is incomplete, and the specification target is a decade behind the ratified X3D 4.0 standard.

X3D 4.0 is now fully ratified as an ISO/IEC International Standard. It includes native PhysicalMaterial nodes directly aligned with glTF 2.0 PBR, Humanoid Animation 2.0 (HAnim2), Web Audio API integration, and inline glTF loading. Simultaneously, the Khronos Group has published a Release Candidate for the KHR\_gaussian\_splatting glTF extension (February 2026), creating a standards pathway for gaussian splat scenes to live inside glTF containers — which X3D 4.0 can inline directly.

This document specifies the engineering requirements for a complete, production-grade rewrite of the Blender X3D plugin that will make Blender the canonical authoring tool for the open-standards 3D web stack — covering X3D 4.0, glTF 2.0, HAnim2, Gaussian Splatting, and interactive X3D scene scripting — and will serve as a keystone for X3D ecosystem rejuvenation.

# **2\. Background & Strategic Context**

## **2.1 The Current Plugin — A Diagnosis**

The existing io\_scene\_x3d addon was built incrementally over many years, primarily targeting the VRML 2.0 / X3D 3.x specification family. It works acceptably for basic geometry and simple Phong-shaded scenes. Beyond that baseline, it fails in ways that are not marginal deficiencies but fundamental structural absences.

### **2.1.1 Known Critical Defects**

* **Texture Export Non-Functional:** Image textures assigned to Blender materials do not appear in exported X3D output regardless of material setup. This has been an open issue across multiple major Blender versions with no resolution.

* **No PBR Material Support:** The Principled BSDF shader — Blender's default since 2.79 and the foundation of every modern Blender material — is not mapped to any X3D output. Metallic, roughness, normal maps, emission, and ambient occlusion channels are all silently dropped.

* **X3D 3.3 Target Only:** The exporter targets a 2015 spec. X3D 4.0 — ratified in 2023 — introduces PhysicalMaterial, glTF inline loading, HAnim2, Web Audio, and numerous other capabilities that are unreachable through the current plugin.

* **Incomplete Animation:** Keyframe animation export is partial and does not support NLA editor outputs, shape key (morph target) animation, or armature-based skeletal animation to X3D's interpolator/sensor graph.

* **No Instancing Optimisation:** Blender's linked duplicates and collection instances — which map perfectly to X3D's DEF/USE referencing system — are expanded into redundant geometry on export, producing unnecessarily large files.

* **No Interactive Scaffolding:** X3D's event-driven ROUTE/sensor/interpolator system — one of its most powerful differentiators from glTF — is entirely absent from the exporter output.

## **2.2 The Opportunity — Why Now**

Several converging factors make 2026 the optimal moment for this rewrite:

* **X3D 4.0 is complete:** The specification is ratified. The PhysicalMaterial node, deliberately aligned with glTF 2.0 metallic-roughness PBR, has stable normative text. The Principled BSDF to PhysicalMaterial mapping is well-defined and tractable.

* **glTF structural alignment:** X3D 4.0's PhysicalMaterial and glTF 2.0's PBR material model share the same underlying equations and parameter set. A Blender plugin that exports X3D 4.0 correctly is simultaneously producing content that inter-operates with the entire glTF toolchain at the material level.

* **KHR\_gaussian\_splatting RC:** The Khronos Group published a Release Candidate for the KHR\_gaussian\_splatting glTF extension in February 2026\. Since X3D 4.0 supports direct inline loading of glTF assets, gaussian splat scenes can be delivered inside X3D scenes through this pathway today.

* **Blender Extensions Platform maturity:** Blender's extensions platform (launched May 2024\) provides a first-class, well-supported path for distributing, versioning, and maintaining the plugin with proper CI/CD.

* **Ecosystem rendering health:** X\_ITE (v12+) and X3DOM are both actively maintained, tracking X3D 4.0 features. The web rendering layer exists and works. The toolchain gap is precisely the authoring side.

# **3\. Goals, Non-Goals & Success Metrics**

## **3.1 Primary Goals**

1. Implement full Principled BSDF → X3D 4.0 PhysicalMaterial export with all texture channels intact.

2. Export X3D 4.0 as primary target; retain X3D 3.3 and VRML 2.0 as optional legacy modes.

3. Implement DEF/USE instancing to accurately reflect Blender linked duplicates and collection instances.

4. Export complete skeletal animation to HAnim2 and keyframe animation to X3D interpolator/sensor graph.

5. Export shape key (morph target) animation to X3D CoordinateInterpolator.

6. Implement glTF 2.0 roundtrip: Blender → X3D 4.0 with inline glTF, and X3D \+ glTF inline → Blender with full material fidelity.

7. Implement gaussian splat passthrough: Blender splat objects → KHR\_gaussian\_splatting glTF → X3D Inline node.

8. Implement interactive scene scaffolding: configurable X3D ROUTE/sensor/interpolator templates for common interaction patterns.

9. Achieve full round-trip fidelity: a scene exported to X3D 4.0 and re-imported to Blender must recover geometry, materials, armatures, and animation with no data loss beyond documented limitations.

* Runtime execution of X3D scripts inside Blender (EcmaScript/SAI interpreter).

* Blender as an X3D browser or viewer.

* Support for deprecated X3D profiles (CAD, DIS) beyond basic geometry passthrough.

* Custom GLSL shader export to X3D ComposedShader nodes (post-v1 consideration).

* Real-time gaussian splat training or COLMAP integration within Blender.

# **4\. Technical Architecture**

## **4.1 Design Principles**

* **Separation of concerns:** The plugin is structured as three independent layers: (1) a Blender Scene Extractor that traverses bpy.data and produces an intermediate representation (IR); (2) an X3D Emitter that consumes the IR and produces X3D XML/JSON; and (3) an X3D Parser that reads X3D and populates bpy.data. No layer has direct knowledge of the other's implementation.

* **Intermediate Representation:** The IR is a Python dataclass graph that is format-agnostic. It contains typed nodes for Mesh, Material, PBRMaterial, Texture, Transform, Armature, AnimationCurve, MorphTarget, Light, Camera, Instance, Sound, and GaussianSplat. The IR is serialisable to JSON for debugging and test fixture generation.

* **Strict X3D 4.0 schema compliance:** All emitted X3D is validated against the normative X3D 4.0 XML Schema and DTD before passing CI. The validator runs as a post-export step in both developer mode and automated CI.

* **Progressive enhancement:** Export options are layered: a minimal "X3D 3.3 compatible" mode produces content renderable by legacy browsers; full "X3D 4.0 PBR" mode enables PhysicalMaterial, HAnim2, and gaussian passthrough.

* **Idempotent import:** Importing an X3D file produced by this exporter must produce a Blender scene that, when re-exported, produces a byte-equivalent X3D file (modulo XML attribute ordering). This is the definitive round-trip contract.

## **4.3 Intermediate Representation — Key Dataclasses**

The IR is the contractual interface between the Blender-side extractor and the X3D-side emitter. All data passed between layers must be expressible as IR nodes. This guarantees testability: both the extractor and emitter can be unit-tested independently against IR fixtures.

### **4.3.1 PBRMaterial Node**

This is the most important IR node. It maps directly to Blender's Principled BSDF and to X3D 4.0's PhysicalMaterial. Every field is optional; absent fields use X3D default values.

| IR Field | Blender Source | X3D 4.0 Output | Type / Range |
| :---- | :---- | :---- | :---- |
| base\_color | Principled BSDF: Base Color (RGB) | PhysicalMaterial.baseColorFactor | Vec3 \[0,1\] |
| base\_color\_texture | Base Color socket: ImageTexture node | PhysicalMaterial.baseColorTexture | TextureRef |
| metallic | Principled BSDF: Metallic | PhysicalMaterial.metallicFactor | Float \[0,1\] |
| roughness | Principled BSDF: Roughness | PhysicalMaterial.roughnessFactor | Float \[0,1\] |
| metallic\_roughness\_texture | Metallic/Roughness socket: ImageTexture | PhysicalMaterial.metallicRoughnessTexture | TextureRef |
| normal\_texture | Normal Map node: ImageTexture | PhysicalMaterial.normalTexture | TextureRef |
| normal\_scale | Normal Map node: Strength | PhysicalMaterial.normalScale | Float |
| emissive\_color | Emission node: Color x Strength | PhysicalMaterial.emissiveColor | Vec3 |
| emissive\_texture | Emission socket: ImageTexture | PhysicalMaterial.emissiveTexture | TextureRef |
| occlusion\_texture | AO node output: ImageTexture | PhysicalMaterial.occlusionStrength | TextureRef \+ Float |
| alpha\_mode | Material blend\_method | PhysicalMaterial.alphaMode | Enum: OPAQUE/MASK/BLEND |
| alpha\_cutoff | Material alpha\_threshold | PhysicalMaterial.alphaCutoff | Float \[0,1\] |
| double\_sided | Material use\_backface\_culling (inverted) | PhysicalMaterial.solid (inverted) | Bool |

### **4.3.2 AnimationTrack Node**

Each AnimationTrack in the IR corresponds to one output channel of a Blender F-Curve or NLA strip bake. It contains: **target\_node\_def** (X3D DEF name of the target node); **target\_field** (X3D field name, e.g. "translation", "rotation"); **interpolation** (LINEAR / STEP / CUBICSPLINE); **times** (list of float seconds); and **values** (list of interpolated values matching the field type). On emit, each AnimationTrack becomes a TimeSensor \+ typed Interpolator \+ ROUTE pair.

### **4.3.3 GaussianSplat Node**

The GaussianSplat IR node holds: **ply\_path** (absolute path to source PLY); **spz\_path** (optional pre-compressed SPZ path); **transform** (4x4 matrix); **sh\_degree** (0–3); and **embed\_in\_glb** (bool — controls whether the GLB is embedded as a base64 data URI in the X3D Inline src or written as a sidecar file).

# **5\. Feature Specifications**

## **FEAT-01: Principled BSDF → PhysicalMaterial Export**

| *Priority: P0 — Blocking. This is the single most impactful defect in the current plugin. No other feature ships before this one is complete and tested.* |
| :---- |

### **5.1.1 Node Graph Walker**

The material.py module implements a recursive node graph walker starting from the Material Output node's Surface input. It must handle the following node topologies:

* **Direct Principled BSDF:** Principled BSDF connected directly to Material Output. All socket values and connected ImageTexture nodes are extracted.

* **Mix Shader (PBR \+ Emission):** Common pattern for emissive PBR materials. Walker detects Mix Shader, identifies Principled BSDF and Emission branches, merges into single PBRMaterial IR node.

* **Texture coordinate transforms:** Mapping node between Texture Coordinate and ImageTexture is captured and emitted as X3D TextureTransform.

* **Non-Color texture handling:** Metallic/Roughness and Normal Map textures are marked non-color in Blender. The IR must preserve the colorspace tag to prevent incorrect gamma conversion in X3D output.

* **Fallback for unsupported topologies:** If node graph is unrecognised, walker falls back to bpy.Material.diffuse\_color \+ specular\_intensity and emits X3D 3.x-compatible Appearance/Material with a warning log entry.

### **5.1.2 Texture Export Modes**

* Referenced: Textures are written to a textures/ subdirectory relative to the .x3d output file. ImageTexture.url is a relative path.

* Embedded: Textures are base64-encoded and written as data: URIs in ImageTexture.url. Produces single-file output. Optional, off by default.

* GLB mode: All textures are embedded in a .glb sidecar (for gaussian passthrough workflows). ImageTexture.url references the GLB buffer view using glTF URI syntax.

## **FEAT-02: X3D 4.0 as Primary Export Target**

| *Priority: P0. All new emission code targets X3D 4.0. The X3D 3.3 emitter is a separate code path and is explicitly labelled as legacy in the export UI.* |
| :---- |

The emit\_x3d.py module emits conformant X3D 4.0 XML. Mandatory structural requirements:

* XML declaration: \<?xml version="1.0" encoding="UTF-8"?\>

* DOCTYPE reference to the X3D 4.0 DTD.

* X3D root element with profile="Immersive" (or "Full" when HAnim2 is present), version="4.0".

* head/meta blocks include generator tag (plugin version), creator (from Blender scene custom properties), and rights (from export dialog optional field).

* All node names use X3D 4.0 normative spelling. No deprecated VRML aliases.

* PositionInterpolator2D, CoordinateInterpolator, OrientationInterpolator, ScalarInterpolator, ColorInterpolator all emitted with X3D 4.0 normative field names.

## **FEAT-03: DEF/USE Instancing**

### **5.3.1 Detection Logic**

The extractor traverses bpy.data.objects and identifies instancing relationships:

* Linked mesh data-blocks (multiple objects sharing the same bpy.types.Mesh) are emitted as one DEF Shape and subsequent USE references.

* Collection instances (COLLECTION type objects) are emitted as DEF Group \+ USE references.

* Particle system instances with the same particle object source are emitted as USE references within a PointSet or via X3D Particle Systems nodes.

### **5.3.2 DEF Name Generation**

DEF names are generated deterministically from the Blender object/data-block name with non-alphanumeric characters replaced by underscores and a prefix applied based on node type (MESH\_, MAT\_, SHAPE\_, GROUP\_). Collision detection ensures uniqueness within the scene scope.

## **FEAT-04: Skeletal Animation — HAnim2 Export**

| *Priority: P1. X3D 4.0's HAnim2 support is a major strategic differentiator. This feature makes Blender the premier authoring tool for X3D character animation.* |
| :---- |

### **5.4.1 Armature to HAnim2 Skeleton Mapping**

The animation.py module maps Blender armature bone hierarchies to HAnim2 HAnimHumanoid / HAnimJoint / HAnimSegment / HAnimSite structure. Mapping strategy:

* Bone names matching HAnim2 standard joint names (e.g. "HumanoidRoot", "l\_hip", "r\_knee") are mapped directly to canonical HAnimJoint DEF names.

* Non-standard bone names are mapped to custom HAnimJoint nodes with a metadata annotation preserving the original name.

* The HAnimHumanoid node is emitted with the Blender armature object's world transform. Scale is extracted and applied to the humanoid loa field.

* Skinning weights (vertex groups) are emitted as HAnimJoint skinCoordWeight and skinCoordIndex fields, referencing a shared HAnimHumanoid skinCoord Coordinate node.

### **5.4.2 Keyframe Animation Export**

For each animated bone channel (location, rotation\_quaternion, scale), a TimeSensor \+ OrientationInterpolator/PositionInterpolator/ScalarInterpolator \+ ROUTE triplet is emitted. NLA editor strips are baked using Blender's bpy.ops.nla.bake before extraction to ensure all procedural modifiers are captured. The bake frame range and step are configurable in the export dialog.

## **FEAT-05: Shape Key (Morph Target) Export**

Blender shape keys map to X3D CoordinateInterpolator nodes. Each shape key produces a key value array in the interpolator, with a TimeSensor driving the key field and a ROUTE connecting TimeSensor.fraction\_changed to CoordinateInterpolator.set\_fraction, and CoordinateInterpolator.value\_changed to the target Coordinate.set\_point.

Relative shape keys (relative=True in Blender) are converted to absolute position arrays at export time by adding the basis shape's vertex positions. The relative flag and value are preserved as X3D metadata on the interpolator node for round-trip fidelity.

## **FEAT-06: glTF 2.0 Roundtrip Bridge**

### **5.6.1 Export: Blender → X3D 4.0 \+ Inline glTF**

When the export option "Embed geometry as glTF Inline" is enabled, the exporter calls Blender's native io\_scene\_gltf2 exporter to produce a .glb sidecar, then emits an X3D scene containing a top-level Transform with an Inline node whose url points to the .glb. This produces a valid X3D 4.0 scene that loads in X\_ITE and X3DOM with full PBR fidelity, leveraging the mature glTF exporter for geometry and materials.

### **5.6.2 Import: X3D with Inline glTF → Blender**

The parser detects X3D Inline nodes whose url references a .glb or .gltf file. These are delegated to Blender's io\_scene\_gltf2 importer. The resulting Blender objects are then positioned according to the enclosing X3D Transform hierarchy, enabling a heterogeneous X3D scene (mix of native X3D nodes and glTF Inline assets) to import coherently.

## **FEAT-07: Gaussian Splat Passthrough**

| *Priority: P1. This feature positions the plugin at the frontier of 3D content creation workflows and directly connects the Blender/X3D ecosystem to the gaussian splatting revolution.* |
| :---- |

### **5.7.1 Splat Detection in Blender Scene**

The gaussian.py module detects gaussian splat objects in the Blender scene by checking for the custom property x3d\_gaussian\_splat \= True, or by detecting objects created by the KIRI Engine 3DGS addon or gsplat Blender integration. The associated PLY file path is read from the custom property x3d\_splat\_ply\_path.

### **5.7.2 PLY to KHR\_gaussian\_splatting GLB**

The module converts the gaussian splat PLY to a glTF 2.0 GLB with the KHR\_gaussian\_splatting extension, following the Release Candidate specification (February 2026). Key implementation details:

* Gaussian attributes (position, rotation quaternion, scale, opacity, spherical harmonic coefficients) are packed into glTF buffer views as typed accessor arrays.

* SPZ compression is applied optionally via the MIT-licensed SPZ library (Python bindings), emitting the KHR\_gaussian\_splatting\_compression\_spz extension. Target compression: \>=80% size reduction vs uncompressed PLY.

* Spherical harmonic coefficients up to degree 3 (16 coefficients per colour channel) are included when present in the source PLY.

* The GLB is written as a sidecar .glb file or optionally embedded as a base64 data URI.

### **5.7.3 X3D Inline Emission**

The emitter wraps the GLB in an X3D Inline node with an enclosing Transform carrying the splat object's world matrix. A metadata annotation records the source PLY filename and gaussian count for reference. The exported X3D scene renders correctly in X\_ITE (which supports KHR\_gaussian\_splatting) when loaded in a browser.

## **FEAT-08: Interactive Scene Scaffolding**

### **5.8.1 Interaction Hint System**

Artists annotate Blender objects with custom properties to request X3D interactive behaviour:

| Custom Property | Value Example | Generated X3D Output |
| :---- | :---- | :---- |
| x3d\_sensor | "TouchSensor" | TouchSensor child node added to enclosing Transform. isActive ROUTE generated. |
| x3d\_onClick\_animate | "MyObjectAnim" | TouchSensor.touchTime ROUTE → TimeSensor.startTime. TimeSensor → animation interpolators. |
| x3d\_proximity\_range | "5.0" | ProximitySensor with size \= range. enter/exit ROUTEs to linked TimeSensor. |
| x3d\_viewpoint | "true" | Viewpoint node emitted at object location/orientation. Camera name becomes viewpoint description. |
| x3d\_billboard | "Y\_AXIS" | Billboard node wrapper with axisOfRotation set appropriately. |
| x3d\_lod\_ranges | "5,20,50" | LOD node generated. Object and its LOD-linked variants assigned to LOD levels by range. |

### **5.8.2 ROUTE Graph**

The scaffold.py module collects all sensor-animation relationships identified during IR extraction and emits a ROUTE block at the end of the X3D Scene node. ROUTEs are emitted in dependency order (sensors before interpolators before targets) to satisfy X3D's forward-reference requirement.

# **6\. Import Specification**

## **6.1 Supported Input Formats**

* X3D 4.0 — XML encoding (.x3d) and JSON encoding (.x3dj)

* X3D 3.0, 3.1, 3.2, 3.3 — XML and Classic VRML encoding (.x3dv)

* VRML 2.0 / 97 — .wrl, .wrz (gzip-compressed)

* X3D with Inline glTF references — .x3d containing Inline nodes referencing .glb/.gltf

## **6.2 Import Pipeline**

11. Parse and validate input against X3D version-appropriate schema.

12. Resolve Inline node references: local .x3d/.glb files loaded recursively; external URLs reported as warnings (not fetched automatically for security).

13. Build IR graph from parsed X3D scene graph.

14. Expand DEF/USE references: USE nodes replaced with deep copies of their DEF originals in IR (Blender will re-detect instancing opportunities during populate step).

15. Populate Blender scene from IR (populate.py).

16. Reconstruct animation: TimeSensor \+ Interpolator \+ ROUTE triplets → Blender F-Curves.

17. Reconstruct HAnim2 skeletons → Blender armatures with bone names and vertex group weights.

18. Report import statistics: node count, material count, texture count, animation track count, unrecognised nodes (with line numbers).

## **6.3 Unrecognised Node Handling**

X3D nodes with no Blender equivalent (e.g. EspduTransform, CADAssembly, GeoLocation) are imported as Empty objects with the X3D node type stored as a custom property x3d\_node\_type, and all node fields stored as JSON in x3d\_node\_fields. On re-export, these custom properties are read and the original X3D nodes are reconstructed verbatim. This preserves semantic content that Blender cannot represent natively.

# **8\. Testing & Quality Assurance**

## **8.1 Test Categories**

* **Unit tests:** Every public function in ir.py, material.py, animation.py, scaffold.py, and gaussian.py has direct pytest unit tests with mocked bpy fixtures. Target: 90% line coverage.

* **Emit / Parse round-trip tests:** For each IR fixture, verify that emit\_x3d.py → parse\_x3d.py produces an IR graph equal to the original under defined equivalence rules.

* **Blender scene round-trip tests:** Curated .blend scene files are exported to X3D, re-imported, re-exported, and the two X3D outputs compared. This catches populate.py regressions.

* **Render comparison tests:** Reference renders are produced from .blend files using Blender's Cycles renderer. The exported X3D is rendered headlessly in X\_ITE and compared using SSIM. Gate: SSIM \> 0.92 for PBR scenes, \> 0.97 for unlit scenes.

* **X3D schema validation:** Every X3D file produced by any export path is validated against the X3D 4.0 XML Schema using lxml. Validation errors are CI failures.

* **Performance benchmarks:** Export time and output file size are tracked for canonical benchmark scenes (small: \< 1k polys; medium: 10k polys; large: 100k polys; instance-heavy: 1k unique \+ 50k instances).

* **Blender version matrix:** CI runs on Blender 4.3 LTS, 4.4 stable, and the rolling main branch daily build. API deprecation warnings are treated as errors.

## **8.2 Reference Scene Library**

The test suite maintains a reference scene library in tests/scenes/ covering the following canonical cases:

* simple\_pbr: Single mesh with full Principled BSDF — base color, metallic, roughness, normal, emission, AO, alpha.

* multi\_material: Single mesh with three material slots, each a different PBR configuration.

* instanced\_forest: 2,000 tree instances using three unique mesh data-blocks. Validates DEF/USE output and file size reduction.

* animated\_character: Humanoid armature (HAnim2 bone names) with 120-frame walk cycle and facial shape keys.

* audio\_scene: Scene with three sound objects mapped to X3D Sound/AudioClip nodes.

* gaussian\_room: Scene with a KIRI-addon gaussian splat object representing a photorealistic room interior.

* interaction\_demo: Five objects with x3d\_sensor properties covering all scaffold templates.

* gltf\_hybrid: X3D scene with one native X3D mesh and two Inline glTF references.

# **10\. Constraints, Risks & Dependencies**

## **10.1 Technical Constraints**

* **Blender Python API:** All code must use the documented public bpy API. Internal/undocumented Blender APIs must not be used, as these break between minor Blender releases. The bpy.app.version guard must be used for any API that changed between Blender 4.3 and 4.4.

* **GPL-2.0-or-later licence:** All dependencies must be GPL-compatible. The SPZ library (MIT licensed) is compatible. No proprietary libraries.

* **No C extensions in core plugin:** The core Python plugin must run without compiled extensions to ensure cross-platform compatibility (Windows, macOS, Linux). The optional gaussian compression path may use pre-compiled SPZ bindings distributed as separate platform wheels.

* **Blender Extension size limit:** The extensions.blender.org platform has a 50MB package size limit. Bundled assets (test scenes, documentation) must be separated from the distribution package.

## **10.2 Risk Register**

| Risk | Severity | Probability | Mitigation |
| :---- | :---- | :---- | :---- |
| KHR\_gaussian\_splatting spec changes before ratification | HIGH | MEDIUM | Implement against RC with abstraction layer isolating spec-specific field names. Finalise in S5. |
| Blender API breaking changes in 4.4 or 4.5 during programme | MEDIUM | MEDIUM | CI matrix includes rolling Blender main build. API guard patterns used throughout. |
| X3D 4.0 parser edge cases in existing X3D corpus | MEDIUM | HIGH | Fuzz test with Web3D Consortium public example archive (2000+ X3D files) from Sprint 1\. |
| Principled BSDF node graph complexity exceeds walker coverage | MEDIUM | MEDIUM | Graceful fallback to diffuse colour. Warning log. Community-reported topologies backlogged for v1.1. |
| HAnim2 bone name mapping for non-standard rigs | LOW | HIGH | Document standard mapping table. Non-standard names preserved as metadata. Not a blocker. |
| SPZ compression library platform support gaps | LOW | LOW | SPZ compression is optional. Uncompressed PLY passthrough is the fallback. Feature ships without SPZ if needed. |

## **10.3 External Dependencies**

* **Blender io\_scene\_gltf2:** The glTF bridge (FEAT-06) depends on Blender's bundled glTF importer/exporter. API calls to this addon are version-gated.

* **lxml:** X3D schema validation in validate.py uses lxml for XSD validation. lxml is included in Blender's bundled Python on all platforms.

* **X3D 4.0 XML Schema:** The normative XSD is distributed with the plugin from the Web3D Consortium's official schema distribution.

* **SPZ Python bindings:** Optional dependency for gaussian splat compression. Distributed as a separate optional dependency. Version pinned to SPZ 1.x.

# **12\. Post-v1.0 Roadmap Considerations**

| *The following features are explicitly out of scope for v1.0 but are architecturally anticipated. The IR design and module structure should not preclude their future implementation.* |
| :---- |

* **ComposedShader export (v1.1):** Map Blender shader node groups marked with x3d\_custom\_shader to X3D ComposedShader nodes with GLSL vertex and fragment shader strings. Enables fully custom rendering effects.

* **Volume rendering (v1.1):** Map Blender volume objects (OpenVDB) to X3D IsoSurface / VolumeData nodes introduced in X3D 4.0.

* **CAD profile support (v1.2):** CADAssembly, CADFace, CADLayer, CADPart nodes for engineering visualisation workflows.

* **X3D SAI scripting scaffolding (v1.2):** Generate X3D Script node templates from Blender Python logic blocks, outputting SAI-compliant ECMAScript stubs.

* **4D Gaussian Splatting (v1.2):** When 4D-GS and LiveGS Blender integration matures, extend gaussian.py to handle temporally animated gaussian scenes with KHR\_animation\_pointer extension.

* **Streaming export for city-scale scenes (v2.0):** Integrate with the Voyager-style progressive LOD streaming approach: export large scenes as X3D scene graphs with progressive Inline node loading based on camera proximity.

* **USD / OpenUSD bridge (v2.0):** Given the active Khronos/AOUSD coordination on aligned gaussian splatting schemas across glTF and USD, a future X3D ↔ USD conversion path becomes tractable.
