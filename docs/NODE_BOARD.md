# The node board: every concrete X3D 4.0 node, and how far this add-on gets with it

One generated table, 260 rows, one per concrete node of the X3D Unified Object Model 4.0 (X3DUOM). Everything between the
markers is written by `tools/node_board.py` from committed measurements, and a test (`tests/test_node_board.py`) pins the
headline counts, so a change to what the importer reads or the exporter writes has to change the numbers in the same commit.

```
python tools/node_board.py --check      # exit 1 when this page is stale
python tools/node_board.py --write      # regenerate it
python tools/node_board.py --markdown   # print it
```

## Where the numbers come from

| input | made by | what it is |
|---|---|---|
| `tools/node_board_nodes.json` | `node_board.py --regenerate X3DUOM` | the 260 nodes, their component, level, base types and the child nodes their fields accept (X3DUOM 4.0, sha256 inside) |
| `tools/node_board_measured.json` | `tools/node_board_probe.py`, in real Blender | the **read** and **written** rung of every node, with the Blender version and validator in its header |
| `tools/node_board_frequency.json` | `node_board.py --frequency REPO[:prefix] ...` | element counts over `git ls-files '*.x3d'` of the project's own repositories, `vendor/` and `node_modules/` skipped |
| `tools/io_sync/parity.json`, `mapping/x3d_fields.json` | existing | the round-trip class, and whether the 3-file mapping corpus contains the element |
| `tools/behaviour_coverage.py` | existing | the four event rungs of the 57 event nodes |

**Read** is measured, not read from source. For each node the probe builds the smallest file the standard lets the node sit
in (the parent comes from the object model's `acceptableNodeTypes`), imports it with the add-on's operator, imports the same
file without the node, and compares the two Blender states (objects, meshes, materials with their node trees, lights, cameras,
worlds, actions, images, curves, node groups, text blocks, custom properties). The rungs: `builds` (Blender data differ),
`graph` (only with the behaviour graph on: it lands in the X3D Behaviour node tree), `carries` (kept as custom properties or
text so a re-export can write it), `structural` (a grouping node: its children are read and the node itself dissolves),
`reported` (dropped, with a line in the import loss report, never silently), `none` (nothing changed), `unprobed`.
`none` is a lower bound: a node that only does something in company (a shader part, a rigid body outside its collection)
is probed alone unless the probe has a file for it (the `OVERRIDES` table in the probe), so `none` for those nodes is
Likely, not Confirmed.

**Written** is observed: the element is in a file the exporter wrote in a run and that file validates against the X3D
schema (`x3d-4.0.xsd`, lxml). The runs: every `.x3d` fixture of this repository imported (behaviour graph on) and exported as
X3D 4.0, the swatch book and the scene fixture, the export suite's three corpus files, and, per event node, the behaviour
graph's own emitter. `writable` means the emitter's source names the element but no run saw it (Suspected).

## "31 written" was an undercount

`docs/MAPPING.md` says the export writes 31 nodes. That is what the three corpus files of the export suite contain (29 of
them concrete nodes of the object model; the other two are the root `X3D` and `GaussianSplats`). The exporter has two more
ways to write nodes that corpus never exercises: primitives and the classic Material kept from an import (Box, Sphere, Cone,
Cylinder, LineProperties, Material, Sound, CollisionCollection: 8 more), and the behaviour graph, which writes any of its
catalogue's nodes (56 of the 57 event nodes observed; 4 of them are also in the corpus). Measured in a run, the exporter
wrote **89** concrete nodes at 607fd01 (add-on 2.8.0), not 31; the table below has the count for the current commit. The 3-file corpus is still the
right instrument for field-level coverage; it is the wrong one for node-level coverage.

### 268 against 260

docs/MAPPING.md counts 268 nodes because x3d.py 4.0.65.8 declares 8 classes that X3DUOM 4.0 has no concrete node for (EnvironmentLight, FontLibrary, GaussianSplats, HAnimPose, InlineGeometry, RenderedTexture, Tangent, X3D): X3D is the document's root element (a statement in the object model; x3d.py derives it from the node base), and the other seven are X3D 4.1 or Web3D extension nodes that x3d.py already carries. Every one of the 260 concrete nodes of the object model is in x3d.py, none is missing. This board counts the object model's 260 because the standard, not a Python binding, is the denominator; the extras are listed in docs/MAPPING.md.

## Batch 1 (2.9.0) and what the probe found

Thirteen rung moves (table "Moved since 2.8.0"). Be exact about what each is:

- **New code, round trip run in Blender, validated:** `Text` and `FontStyle` (a Blender text object, imported or made in
  Blender, is written as Text; extruded, bevelled, offset or modified text stays a mesh), `Extrusion`, `ElevationGrid` and
  `Rectangle2D` (kept on the mesh like a Box and written back while no vertex moved; an ElevationGrid with a Color, Normal
  or TextureCoordinate child is not kept, because the node could not carry it). `tests/test_node_board_batch_bpy.py`.
- **Existing support the earlier runs never exercised:** `WorldInfo`, `MetadataSet`, `MetadataString`, `MetadataDouble`,
  `MetadataInteger` and `Color` (on a line set) were already written; no corpus file or fixture contained them, so the board
  could not call them observed. `tests/node_board/writable_nodes.x3d` now does.
- **Read:** a bare `<Sound>` (no `maxBack`, `maxFront`, `minBack`, `minFront`) stopped the whole import with a `TypeError`
  (the probe found it: `Sound` and `AudioClip` read `none` because the import failed); the standard's defaults now stand in.
  `FontStyle style="BOLD"`, the X3D 4.0 SFString form, was read as an MFString and dropped; both forms are read now.

Found and not fixed:

- The export of `tests/behaviour/probe-pick.x3d`, `probe-pick-geometry.x3d` and `pick-fallback/probe-pick-fallback.x3d`
  (import with the behaviour graph on, then export) does not validate against x3d-4.0.xsd: a `Box`, `IndexedLineSet` or
  `Coordinate` is written where its parent does not accept it (the pick sensors' `pickTarget`/`pickingGeometry` content). The
  board counts no element from a file that fails validation. Behaviour lane; left alone.
- `Color` is written for line sets but not for faces: a face set's per-vertex colour is always `ColorRGBA`, and about ten
  tests pin that. Equivalent in X3D; a candidate change, not made.
- The read probe is isolated-node differential. `none` for a node that acts only in company (shaders, rigid bodies, sensors
  that need a body in the world) is Likely, not Confirmed, and the `OVERRIDES` table in the probe is where to add its file.
